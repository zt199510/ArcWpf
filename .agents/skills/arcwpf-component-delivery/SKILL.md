# ArcWpf 组件交付

先读 [计划](../../../docs/plan.md) 与已有组件规格，识别当前阶段和依赖。遵循用户当前范围；不要把小任务扩展成全库重构或未经请求的发布。

## 按缺口推进

- 缺来源/规格：读取同级 [来源分析 Skill](../arcwpf-source-analysis/SKILL.md)，补齐实现所需信息。
- 需要控件代码：读取 [控件开发 Skill](../arcwpf-control-authoring/SKILL.md)。只有专门主题/动效问题才再读对应 Skill。
- 需要验收：读取 [界面验证 Skill](../arcwpf-ui-verification/SKILL.md)，使用真实结果判断退出条件。

这些步骤是当前智能体的工作路由，不要求创建子智能体或开启新聊天。

## 开工前置

先确认来源分析 Skill 的“开工闸门”已完成（Registry 源码已冻结并有 manifest）。未完成时先补齐，再进入实现；不得以“仅参考行为”为由跳过。

## 重复反馈的修复

用户再次反馈同一组件“还原不好”或同一缺陷仍在时，先执行[复刻规则](../../../docs/replication-workflow.md#与原版不一致反馈的处理)第 3 条，再动代码：

1. 列出“来源部件/状态/动效 → WPF 模板部件 → 当前实现”的对照表，标出缺失、错误和静态代替过渡的项。
2. 在验证记录写明前几轮的误判原因。
3. 按对照表一次修完；不在原模板上继续调参数。

## 交付契约

1. 对齐规格与真实 API，明确暂缓功能和与原版差异。
   核对 [来源规范](../../../docs/sources.md) 中的优先级与冻结记录；还原目标和 WPF 回归基准分别维护。上游更新先记录差异和采用理由，不直接覆盖基准。
2. 将示例加入 Gallery，展示主要状态、绑定和适用键盘交互；共享库不得依赖示例代码。
3. 运行与改动相关的构建/测试和实际窗口验证，更新结果；不能仅因代码写完就标记已验收。
4. 同步 API 用法、来源/许可记录和里程碑状态。对未测场景保留“待验收”及原因。

交付前增加一次模板布局烟雾检查：在真实窗口中确认滚动区域有有限高度、超出内容可滚动、每个主要条目可用鼠标命中并触发预期状态；确认外部控件尺寸不会裁剪模板内标签或状态。程序化测试覆盖事件和属性，但不能替代这次窗口检查。

对 Web → WPF 组件，交付前逐项核对“来源结构 → WPF 布局单元 → 实际坐标/尺寸”。只把已确认的来源值写入规格；无法确认的值保留为 WPF 适配项并记录测量结果。不得因为功能测试通过就跳过外形、内容裁剪或操作区位置检查。

最终报告包含完成内容、验证证据、剩余限制和下一步。普通开发不自动执行提交、上传包或公开发布；这些操作依用户具体任务授权。

## 完整度收口

遵循 [复刻规则](../../../docs/replication-workflow.md)。开工前确认参考卡和规格矩阵；交付前逐行核对API、外形、内容组合、状态、动效、输入/主题与Gallery。不得在交付时才用“首版”解释未完成的已约定项。

Gallery默认提供可对照主示例与独立扩展测试区；既有已获用户确认的示例调整另记范围，不为套统一布局而无关重做。

最终同步已实现、约定暂缓、未验证、已知差异及证据入口。报告本次实现完成与通过视觉验收是两个结论；构建/单测不能替代用户或实际窗口结果。

编码前在规格中写好动效核对表（触发、参数、WPF 位置）；没有这张表不开始编码。收口时按[动效逐项核对](../../../docs/replication-workflow.md#动效逐项核对)检查必做缺项，按[同一构建版本的验收](../../../docs/replication-workflow.md#同一构建版本的验收)确认最终修改已有对应证据。缺项继续实现；可见问题尚未复验则明确“已修改，实际效果待复验”，不能将已知未实现项降为待验收后宣布完成。
