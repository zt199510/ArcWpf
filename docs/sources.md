# 来源、复用与证据

## 参考优先级（2026-10-25 项目基线）

按问题类型选择权威来源，不给仓库排一个永久总顺序。用户明确的产品要求优先于默认还原目标，差异在组件规格中记录。本节确立规则，尚不代表首批组件的来源已经下载或冻结。

| 问题类型 | 第一依据 | 补充参考 | 实施原则 |
|---|---|---|---|
| 色彩、圆角、间距、字体、图标 | 固定版本 Arc 令牌和组件源码 | 同版本实际渲染、文档 | 保留视觉语义；渲染差异注明容差 |
| 动画参数、状态变化、交互意图 | Arc 源码及实际行为 | 动效文档、TKCode.Arc 算法 | 参数查源码，体验用运行核对，调度按 WPF 适配 |
| 组件用途、变体与范围 | 固定版本 Arc 文档和目录 | 源码、TKCode.Arc 清单 | 交付范围由本项目计划决定 |
| 属性、绑定、命令、模板、生命周期 | WPF 官方机制及项目架构规范 | TKCode.Arc 设计思路 | 不复制其他框架专属 API |
| 键盘、焦点、IME、无障碍 | WPF 原生行为与 Windows 使用习惯 | Arc 交互意图 | 保留操作目的，不破坏桌面输入体验 |
| 纯算法、基础设施 | 经验证的正确性、依赖成本与许可 | Arc 与 TKCode.Arc 实现 | 不因代码更近就自动选用 |
| 是否引入回归 | 已审查的 ArcWpf 基准与行为契约 | 固定 Arc 目标 | 不直接用实时网站替换回归基准 |

外观和交互意图追随 Arc，运行机制遵循 WPF，TKCode.Arc 提供移植经验。TKCode.Arc 与原站不同的地方不能自动成为 Arc 原始要求。

## 原站资料内部冲突

先核对版本、主题、变体、字体和视口。不同日期的文档、源码和部署页面不能假定相同版本。精确参数与分支条件查源码，呈现和过程通过运行观察核对，用途和公开变体参考文档。

仍有冲突时记录双方证据、临时选择及待验证项，不能默默选择更容易实现的一方。原版明显缺陷不必照搬，但 WPF 修正须有理由和测试，不伪装成原版行为。

## 证据等级

标注到具体结论，同一结论可有多种证据；验证状态独立记录。

| 标记 | 必要记录 | 证据边界 |
|---|---|---|
| 源码确认 | 固定版本、文件、符号或行号 | 不证明部署网站运行同版源码 |
| 文档确认 | 版本/日期、页面与章节 | 不证明实际行为完全符合文档 |
| 运行观察 | 环境、步骤、状态、截图或操作记录 | 单张截图不证明键盘模型或精确弹簧参数 |
| 暂定设计 | 假设或 WPF 自主选择、理由、验证方式 | 不能写成 Arc 原始事实 |

例如“原版参数已源码确认，WPF 等效效果待验证”是有效状态。来源缺失时不编造数值。

## 首批来源冻结步骤

范围是 Button、Input、Switch、Popover 及 Switch 弹簧行为，不因此扩展成全量抓取或开始实现。

1. 在组件规格登记目标变体和待提取资料，初始状态为待采集。
2. 获取实际需要的 Arc 源码、文档、令牌及动效依赖，记录来源 URL、获取时间、文件清单、SHA-256，以及可取得的官方版本。哈希仅标识内容，不证明授权或真实性。
3. TKCode.Arc 固定完整提交 SHA，并引用具体文件，不只记录 main 链接。
4. 上游没有统一版本时用明确标为“项目采集批次”的标识，逐文件记录日期与哈希，核对共享依赖；不把采集日期冒充官方版本。
5. 来源清单、关键提取结论随规格版本化；临时缓存放 work/references/。需要长期复现且许可允许的副本放 tests/Baselines/References/。不能保存时记录复现限制，不只依赖被忽略的缓存。
6. 来源、运行证据或许可缺口单列。已明确部分可继续；未完成采集不得预填版本、哈希或许可结论。

开始实现前应能说明：参考哪一版、哪些变体、哪些事实已确认、哪些是 WPF 选择。组件规格分别标记待采集、部分固定、已固定。

## 还原目标与回归基准

- 还原目标是固定 Arc 来源及观察记录，用于检查视觉与交互意图的一致性。
- 回归基准是审查通过的 ArcWpf 截图、行为预期和环境，用于检查后续退化。
- 首次接受 WPF 基准前，对照还原目标审查，列明允许差异。稳定的错误截图不能因此成为合格基准。
- 更新基准记录原因、前后差异和实际审查结果；修复移植偏差与引入上游新行为分别记录。
- 静态基准不替代动画、焦点、IME 验证，执行 [验证规范](verification.md)。

## 冲突决策与升级边界

普通取舍记录在组件规格：冲突、备选方案、采用方案、理由、影响范围、验证方式和状态。跨组件决策在 docs/decisions/ 下建立真实决策文件，各规格引用；有实际决策再创建文件。

不改变公开契约的内部实现、等价模板结构、已允许的渲染容差、保持绑定和 IME 的原生适配可直接处理。只有改变明确产品要求、放弃已承诺交互、缩减支持平台、引入付费依赖，或存在无法从授权推断的明显产品体验选择时，准备方案和证据交用户决定。只暂停依赖该决定的部分，不为常规工程选择增加审批。

以下是规则应用示例，不是已验证的实现决定：

| 场景 | 处理 | 验证 |
|---|---|---|
| Input 的 Web 编辑机制不适用于 WPF | 保留 Arc 外观，采用 WPF 原生编辑与绑定契约 | 中文合成、选区、撤销、验证与双向绑定 |
| Popover 宿主不同 | 按跨窗口边界、定位和焦点需求比较 Popup/覆盖层，M1 决定 | Escape、外部点击、主题、屏幕边缘、跨 DPI |
| TKCode.Arc 半径与 Arc 不同 | 核对版本/变体，原站视觉依据优先并记录差异 | 固定主题/字体/DPI 下的实际渲染 |

## 上游更新规则

开发按冻结来源推进，不自动跟随源站。用户要求同步或发现影响当前组件的重要上游修复时，先评估旧/新来源、变更内容、受影响组件/API/视觉/许可，记录采用或暂缓理由。

采用后同步规格和来源清单，重验受影响场景，审查后再更新 WPF 基准。保留旧标识以便回退；同一组件不无说明混用版本。本规则不创建监控任务或定期更新义务。参考优先级不等于复用许可，阅读、行为参考、直接复制仍分别记录。

## 来源记录

每次用于实现的来源记录：URL/仓库路径、提交或版本、获取日期、必要时内容哈希、文件清单、版权与许可、复用方式（直接复制/修改/行为参考）、对应组件。下载副本放 `work/references/`；只有明确需要且可再分发的资源进入产品目录。

规格区分“来源事实 / WPF 设计选择 / 尚待验证”。来源缺失时先记录差异和合理假设，不能把推测写成原版属性、尺寸或动画参数。

不抓取未获授权的付费实现；免费组件也要保留适用的版权与许可。复用代码、字体和图标时，在真正引入时建立第三方清单与所需许可文件。首批源码参考及许可记录见 [采集报告](references/2026-10-25-initial.md)；字体二进制尚未下载，产品实现尚未引入第三方代码。

ArcWpf 自身许可证在发布准备时明确决定；不将参考项目的许可证自动视为所有依赖及本项目的统一许可。
