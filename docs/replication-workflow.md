# 组件复刻与交付规则

适用于完整组件移植及视觉缺陷定位；局部文字修改不必执行完整流程。用户明确的范围优先，延期的截图/实际交互不阻塞已明确的代码工作，但对应验收不能标为通过。

## 先定位问题层级

| 层级 | 核查内容 | 本项目经验 |
|---|---|---|
| 控件外形 | 轮廓、圆角、描边、颜色 | Switch的椭圆不是Gallery排列问题 |
| 控件内部 | 图标、文字、占位、滑块坐标 | Input必须比较占位与首字符实际起点 |
| 状态和动效 | 触发、先后顺序、打断、退场 | Button有四变体不等于内容动画齐全 |
| 展示容器 | 预览宽度、背景、居中、演示文案 | 原版主示例不能被自创邮箱表单替代 |

收到模糊反馈时先结合截图、模板和布局测量定位。没有证据时说明尚未定位，必要时问具体部位；不要先修改另一层。明确的局部问题直接修复，不扩展为重做页面。

### “与原版不一致”反馈的处理

1. 先打开冻结源码，逐项对照当前实现，写出具体差异（状态、元素、参数），再修改。没有冻结源码时先执行来源分析闸门。
2. 用户描述的是现象，不是实现方案。把反馈翻译成源码中的对应行为；源码中不存在的状态、阶段或动效不得自行添加。
3. 同一问题连续两轮修改仍未解决，停止调参，重新核对来源与模板部件是否齐全，并在验证记录写明前几轮的误判原因。

反例（ActionButton，2026-10-28）：未取源码，四轮修改依次删除 Spinner、让箭头旋转、自创 280ms 完成阶段；源码实际为 arrow→spinner→check 三相图标，完成即进入成功态。

## 参考基准

每个组件在docs/references/components/保存参考卡，链接冻结源码与规格，不复制整份源码。填写主示例文案/初始值、显示状态、组件几何、展示容器和字体环境。未知项写待核对，不能编造为原站事实。

证据采用描述性标签：源码确认、页面文本/HTML/CSS确认、用户截图、运行观察、WPF适配、待核对。不同证据回答不同问题，不作一条简单高低排名：截图证明静态外形，不能证明键盘顺序；源码证明参数，不能证明Windows最终渲染。注明采集批次/版本/哈希和是否持久化。临时截图归档后保留SHA-256；未知DPI、主题或浏览器环境如实注明。

原版还原目标和WPF回归基准分开。既有数值不能因为新测试失败而自动改成当前实现；源站更新也不能无记录地替换已冻结目标。

## 开发前的范围矩阵

规格以“交付项 / 本次范围 / 实现状态 / 证据 / 剩余差异”列示API与绑定、外形、内容组合、状态、动效、输入/自动化、主题及Gallery。范围只能为本次必做、明确暂缓、不适用；实现状态单独填写。已约定必做项不得自行降为暂缓，新增发现先如实记录并处理，不能以“首版”解释未完成承诺。

矩阵写清“尚未实现”与“已实现但未验证”的区别。历史用户通过反馈不覆盖后续修改版本；没有提交号时使用日期和明确变更范围，禁止虚构版本。

## WPF适配检查

| 原意 | 风险 | 做法/证据 |
|---|---|---|
| CSS超大胶囊圆角 | WPF可能变椭圆 | 固定高度时用半高半径，检查平直段与圆端；Switch为12/9 |
| 原生文本Padding | 编辑宿主再次应用边距 | 一个位置负责文本Padding，比较GetRectFromCharacterIndex与占位坐标 |
| 居中图标 | 字符基线不等于可见形状中心 | 使用矢量并检查形状边界；复杂光学居中保留人工验收 |
| Web字体与CSS颜色 | 系统回退/色域转换不同 | 保留字体与颜色转换差异，不能声称像素一致 |
| CSS视觉时长 | 不等于固定补间时长 | 写明WPF近似、速度是否连续、收敛阈值与长帧行为 |
| 原生编辑/命令 | 为动画改写数据或重建控件 | 保留Text、Width、命令与DataContext绑定，只动画内部部件 |

这些是已证实的适配风险，不要求所有控件都使用同一圆角、同一偏移或同一动画。新宿主/新运行时必须重新测量，不能把Input的2 DIP补偿推广给所有文本控件。

### 原生行为与视觉装饰分别决定

保留WPF原生选择、键盘导航、焦点与自动化能力，不代表采用或新增WPF默认外观。边框、焦点环、阴影和状态动效应有Arc来源证据或用户明确要求；不能仅以“原生惯例”或“更易用”为由增加复刻目标之外的装饰。

焦点能力与焦点视觉分别核对：先查组件及相关全局样式，区分选中态、鼠标聚焦态、键盘聚焦态，再选实现机制。`FocusVisualStyle`只是实现键盘焦点装饰的手段，不是默认必加项；原版明确只有选中背景时，不额外叠加深色焦点框。不能因本次SegmentedControl修正就统一取消其他控件的焦点提示。

来源不完整时，将焦点视觉记为待核对，继续实现已明确的键盘行为，不把推测写成原版事实。确因平台限制或已明确的可访问性要求需要视觉差异时，在组件规格记录依据、采用方式与影响；普通内部实现不额外增加审批步骤。

验收分别核对焦点是否到达、操作是否生效、最终绘制了什么。焦点事件、属性或导航测试通过不能证明装饰符合原版；检查范围应覆盖相关的鼠标选择、键盘进入/切换和失焦状态。实际观察按用户授权执行，未运行时保留待验收，不据此宣称外观通过。

## 动效逐项核对

完整组件交付或“缺少特效”反馈，先从冻结来源建立动效清单。检查 CSS transition/keyframes、状态选择器、组件动画参数及共享令牌，不只检查显式动画组件。按实际来源分别列出颜色、透明度、缩放、模糊、位移、布局变化、进入/退出、悬停/按压；来源没有的效果不自行添加。

每项关联“触发状态 → 属性与参数依据 → WPF 实现位置 → 验证证据 → 剩余差异”。来源无法确认的项目标待核对；实现缺失不能记作“已实现但待验收”。已有缩放动画不能代表颜色过渡也完成，静态 Trigger 切换也不能代表过渡已复刻。必做动效缺失时继续实现；不能仅补一条限制说明就收口为实现完成。

## 显隐与占位布局回归

适用于清除按钮、状态图标、错误说明等显隐，以及“尺寸变化/占位/跳动”反馈。先依据来源确定应保留空间还是应重排；不要统一规定所有部件固定占位。

- 同时观测控件外框、文本/内容宿主、显隐部件与父容器。记录实际宽高及相对同一稳定祖先的位置，区分内部挤压、整框变宽和整页横移。只断言槽宽或 Width 属性不能证明整体布局稳定。
- 检查父级 Auto/* 测量、居中、滚动条显隐及业务内容变化。控件自身与 Gallery 分开复现；未排除内部布局问题前，不把缺陷全部归因于 Gallery。
- 对受影响路径覆盖显隐前、过渡中、完成后和反向切换；输入控件按缺陷加入空值、长文本及窄容器。来源允许重排时验证约定的变化，不要求所有坐标恒定。
- 回归断言应复现用户可见现象，优先证明旧实现失败、新实现通过。若无法运行旧版本，如实记录限制，不声称已证明根因。程序化测量与实际窗口对比分开记录。

## 动画终态回归

适用于新增或修改动画终态、退场清理，以及闪烁/旧状态重现的修复；不扩大为无关静态修改的测试要求。

1. 记录动画属性归属：使用方公开属性、模板/Trigger属性，或动效引擎独占的内部属性。列明动画期间的当前值、目标值、持久基值及清除后的值来源。
2. 在STA/Dispatcher消息循环中实际推进WPF动画时钟，覆盖过渡、完成、时钟移除及后续刷新。等待应有明确完成条件或有界超时，不能用阻塞UI线程的Sleep替代消息处理。
3. 检查最终有效值保持正确、自有时钟得到清理；按缺陷触发相关的悬停、按压、主题刷新或快速反向，确认旧状态不重现。不要求每个局部修复跑遍所有无关组合。
4. 保留能区分旧实现和修复实现的回归。纯弹簧计算、目标值断言、未加载状态和Off模式可作补充，不能替代动画完成路径。程序化时钟结果与实际窗口视觉结论分别记录。

### CheckBox取消选中案例（2026-10-26）

取消选中后，内部填充淡出到0，但清除动画时钟后Opacity恢复默认1，造成黑色方块闪回。程序化回归实测修复前为1、修复后为0，并检查后续刷新仍为0。原因和结果见 [CheckBox验证记录](verification/2026-10-26-checkbox.md)，长期回归见 [CheckBoxTests.cs](../tests/ArcWpf.Tests/CheckBoxTests.cs) 中UncheckFadeStaysTransparentAfterAnimationCompletes。

该例说明不能依赖SetCurrentValue在动画失效后保持目标值。修复对动效引擎独占的PART_Fill/PART_Mark.Opacity保存持久基值；这不是将所有SetCurrentValue改为SetValue的通用规则。公开属性、绑定、动态资源与模板Trigger仍须保留各自控制权，不以修复闪烁为由覆盖它们。

## Gallery与验收

主示例使用已确认的参考文案、初始值、状态和尺寸约束；尺寸必须区分控件几何与容器宽度。额外绑定、禁用、错误、长文本示例放在独立扩展区域，不自动改动现有已获用户确认的页面。

Gallery 中每个要展示的状态必须可区分：各状态文案不同（如 Label 与 PendingLabel 不能相同），Pending 时长足够观察。不要在示例中设置模板不响应的继承属性（如 ActionButton 上的 `Variant`），以免看起来像已支持。

每项验收写触发步骤、可观测结果、容差及依据。例如Input起点差<=0.5 DIP是本项目程序化测试容差，不是原站规范；Switch平直段像素测试只证明当前96 DPI离屏轮廓。

结果分别记录：
- 构建/逻辑：编译、绑定、事件、数学算法。
- 布局测量：实际坐标/尺寸/基线，不能只断言属性值。
- 离屏渲染：已记录尺寸/DPI/主题的像素或几何检查。
- 实际窗口：输入、焦点、IME、弹出窗口与显示动画。
- 用户反馈：原话、对应变更范围、日期、明确覆盖项与未知项。

前三类通过不能推出后两类通过。自测发现问题先修复，不把本可执行的检查全部转给用户。测试必须能区分缺陷与正确行为；不为每次小修改增加镜像实现的测试。

## 同一构建版本的验收

视觉或交互修复需将“源代码变更 → 构建输出 → 实际运行窗口 → 验证证据”对应起来。记录输出绝对路径、构建时间以及程序集哈希或其他可区分构建的标识；仅提交号不足以标识未提交修改。确认窗口对应的进程/可执行文件路径，不能把旧实例当作最新代码。

修复前后使用可比的主题、动效模式、窗口约束、数据与操作步骤。最终影响行为的修改之后，重验受影响路径；修改前的截图或测试不能自动覆盖最终版本，也不要求因此重跑无关全量检查。静态截图只能证明静态结果，动态过程需对应的运行观察或时间序列证据。

工具被用户输入保护阻断、窗口被遮挡或运行版本无法确认时，停止推断窗口结果，继续独立可执行验证，并记录具体缺口。尊重用户延期，不把窗口验收变成编码前置条件或反复请求授权。

## 完成与暂停边界

交付报告列出已实现、约定暂缓、未验证以及已知差异。只有本次必做实现项完成才报告“本次实现完成”；视觉/专项条件不满足时使用“待验收”，不声称完整还原。用户暂停某类检查时保留缺口并继续独立工作，不反复要求授权。

用户反馈的可见问题尚未在最终版本复验时，报告“已修改，程序化检查通过，实际效果待复验”，不要笼统宣布“问题已解决”。用户再次反馈同一问题时，重新核对其运行版本和原触发路径，将此前结论视为待复核；不能只重复已通过的窄范围测试。
